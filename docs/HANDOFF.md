# Handoff — Tanuki Rush Mobile Edition

Updated 2026-11-14. For user-facing build and release instructions, see [README](../README.md).

## Current scope

- Original Three.js game by tanuu5, MIT. This edition supplies a Flutter Android shell and adds English UI, offline daily missions, local token rewards, cosmetic boost trails, ranks, streaks and settings. Preserve the original credits and licenses.
- Browser preview, tests and production bundle use `tanuki-rush/`; run `python3 tools/build_web_assets.py` after game edits to refresh `mobile/assets/web/`.
- No online database or leaderboard is connected. [DATABASE.md](DATABASE.md) recommends Supabase for a future opt-in online phase and outlines required security and privacy work.
- Android progress/settings are stored in private SQLite (`LocalGameDatabase.kt`) through a serial, validated Flutter bridge. `src/storage.js` bootstraps before the Game/haptics read anything, migrates the old fixed-origin keys once, and replays a revisioned localStorage pending-write journal. SQLite wins after migration; failures block startup or show a native retry warning. Browser builds still use localStorage. The renderer remains Three.js in a WebView.
- `gameStoragePort` is fixed at `43853`; do not change it: legacy keys and the journal are scoped to the full origin. Old random-port builds cannot automatically migrate saves. A port conflict fails closed. Uninstall, app-data clearing, key changes and disk failures can still lose progress; there is no supported backup.
- Android reminders are opt-in and off by default. `flutter_local_notifications` requires Java desugaring in the app Gradle file.

## Verification in this workspace

- `npm test` covers crash and invulnerability semantics, audio scheduling and recovery/lifecycle races, plus deterministic missions, once-per-day bonuses, purchases, save migration, streak dates and rank thresholds.
- `npm run test:touch` simulates actual touch/pointer events in portrait and landscape on the bundled game; it verifies movement, multitouch boost, jump, cancellation, pause/resume and no page scrolling. `npm run test:gameover` tests car/truck crashes, falls, the one optional revive, score/pickup integrity, keyboard activation and fresh-run retry in both orientations. Browser tests are not a physical-device playthrough. An older bot completed the course before these crash-rule changes; it does not verify the current difficulty.
- A Pixel 8 Pro user confirmed the 1.0.1 preview fixes steering, but later reported sound cutting out when BOOST is pressed/held, then returning. The exact cause is unconfirmed. In a headless browser probe, stage music continued during BOOST but the old continuous effect was louder than the music (average bus RMS about 0.162 vs 0.102); this does not explain or reproduce a complete device audio loss. Preview 1.0.3 simplifies and lowers the BOOST effect, extends music lookahead, and ensures a crash/restart stops the BOOST loop. `npm run test:audio` measures music, BOOST and post-limiter output together during held BOOST (including live rendered gameplay), repeated taps and a 220 ms simulated main-thread stall, as well as suspension, closure, mute, pause and reset. The earlier automatic recovery and manual Pause → Settings → Restore Audio → Reset remain. Physical-device confirmation is still needed.
- In flutter_inappwebview_android 1.1.3, the `disableHorizontalScroll` and `disableVerticalScroll` flags intercept or rewrite `ACTION_MOVE`. Both must remain false in `mobile/lib/game_webview_settings.dart`; CSS disables scrolling and native overscroll remains off. A Flutter settings test guards those flags, but a browser test cannot reproduce native event interception.
- This sandbox does not have Flutter, Java or Android SDK installed. GitHub Actions compiles the Android code, tests the SQLite helper with Robolectric and runs Flutter tests. The 1.0.3 build passed [CI](https://github.com/mwijay12/tanuki-rush/actions/runs/42650024962); inspect the newest run and [Releases page](https://github.com/mwijay12/tanuki-rush/releases) for the SQLite preview. No emulator or physical device is available in this workspace.
- The root GitHub Actions workflow builds an artifact and can publish a debug-signed pre-release when the pushed commit message contains `[release-preview]`. A preview is **not** production signing. Each runner may generate a different debug key, and uninstalling a previous build to change keys deletes progress.
- 2026-11-09 incident: the 1.0.4 preview hung on an empty blue screen (Android window background only — status bar visible, back button dead, so Flutter never painted its first frame) on a flagship phone. 1.0.3 and 1.0.4 were released ~90 minutes apart with no hardware testing, and their commits were never merged back to `main`. No deterministic code cause was found: the 1.0.1→1.0.4 Dart/native startup path is unchanged and the toolchain is pinned, so the prime suspects are a wedged install, a one-off bad artifact, or a flaky pre-frame platform-channel hang. 1.0.5 hardens startup (`runApp()` is never blocked by platform channels, every boot wait has a timeout with a visible error + retry, first-frame and fatal-error logcat breadcrumbs) and adds a CI emulator boot test (`tools/ci_boot_test.sh`) that fails the build if the APK never paints. Still pending: the 1.0.1-vs-1.0.5 on-device bisect to confirm whether the cause was the artifact/install or the device.
- 1.0.5 still hangs pre-frame on the Pixel 8 Pro / Android 17 (installed as an update over 1.0.4), ruling out every Dart-side startup theory. Prime suspect is now the engine/renderer on the new OS (Impeller on Tensor/Mali + Android 17, possibly a Vulkan-init hang with no GLES fallback). CI now also boot-tests API 36/37 emulators (`boot-newer-apis` job) to try to reproduce it with logs. Decisive user test: does the 1.0.1 APK boot on that phone today?
- 2026-11-14: that CI job **reproduced the bug**. In run [42977875935](https://github.com/mwijay12/tanuki-rush/actions/runs/42977875935) the API 34 leg passed and both newer legs (API 36 and API 37) failed at the boot smoke test with the *same* x86_64 debug APK. So the hang is OS-version dependent — not a wedged install, not a one-off bad artifact, and not Dart startup code (which is identical on all three legs). The run's logcat/screencap artifacts could not be retrieved from this sandbox (Actions result storage is outside the allowed hosts), so `tools/ci_boot_test.sh` now reports phase markers, `sys.boot_completed`, the app process state, the resumed activity, the display rotation, the SurfaceFlinger graphics backend and an explicit verdict line, which separates "emulator never booted" from "process never started" from "engine never painted".
- 1.0.6 adds a **native boot watchdog** (`BootWatchdog.kt`, wired in `MainActivity.onCreate`). `FlutterActivity` swaps `LaunchTheme` for `NormalTheme` before Flutter draws anything, so a pre-frame hang shows exactly what the user reported: the empty `#0A1A44` window background with a dead back button. Dart timeouts cannot fire because the Dart UI never runs. The watchdog polls `FlutterRenderer.isDisplayingFlutterUi()` every 500 ms and, after 12 s with no frame, adds a plain Android view (built in code, no new resources) over the content view with the device model, Android release, API level, how long it waited, and Retry/Close; it removes that view if a frame ever arrives, so it can never trap a working game. Timing logic has no Android imports and is covered by `BootWatchdogTest` in the ordinary JVM unit-test run. **This does not fix the engine hang** — it ends the silent dead screen and turns it into a photographable field report.
- Rejected: the unmerged branch `arena/edef3682-tanuki-rush` (1d21f7f, "Fix: Pixel 8 Pro / Android 17 blue status bar & splash freeze"). It placed `android:windowDrawsSystemBarBackgrounds` and `android:fitsSystemWindows` on `<activity>`, where they are not activity attributes (aapt2 links them because both exist in the framework, and the platform then ignores them); added `<meta-data android:name="android:windowLayoutInDisplayCutoutMode">`, which nothing reads — cutout mode is a theme `<item>` and belongs in `values-v27/styles.xml`; changed a real newline into a literal `\n` in the gate's error string; and moved `_configureSystemUI()` from `main()` into `_GameGateState.initState()`, which cannot matter because both run after `runApp()`. Nothing in it touches a pre-frame hang. The sound parts of the abandoned work — 92a8688 (1.0.5 release notes) and 7c07031 (the newer-API CI legs) — were cherry-picked into this branch instead.

## Next steps

1. Read the `boot-newer-apis` verdict on the newest run before anything else. If it says the watchdog armed but no frame arrived, the rasterizer is the next experiment: build **one diagnostic APK** with `io.flutter.embedding.android.EnableImpeller` set to `false` in the manifest and run only the API 36 leg against it. If that build paints, the hang is Impeller/Vulkan bring-up and the decision becomes ship-without-Impeller versus wait for an engine fix; if it still does not paint, the rasterizer is exonerated and the remaining suspects are the landscape-locked activity and WebView bring-up on the new OS. This is deliberately *not* shipped blind: it changes rendering on every device, including the ones that work today, and it cannot be tested in this sandbox (no Flutter, Java or Android SDK). Check first whether the pinned Flutter 3.47.9 still honours that flag.
2. Confirm the rest of the GitHub Actions run is green, then install its APK on physical phones. On the Pixel, repeatedly tap and hold BOOST during normal play, listening for both music and JUMP/BOOST, and report whether sound drops out. If it stops, try automatic recovery and Pause → Settings → Restore Audio → Reset. Crash/fall, test the one free revive and the no-revive second failure, retry from the start, and complete a run. Also check both orientations, touch controls, haptics and optional notifications. If the boot watchdog screen appears, photograph it: the model, Android version and wait time in it are the report.
3. On a disposable test installation, install the previous fixed-origin build, create progress/settings, then perform an **in-place update signed with the same key**. Confirm migration, restart/force-stop persistence, offline play and the native storage status. Test disk-full/error recovery where practical. Existing debug previews may have different signatures; do not uninstall a user's valuable save.
4. Obtain and securely back up a long-lived release keystore and design/test an export or backup before production. Never commit or paste credentials.
5. Only after local storage is verified, consider the opt-in Supabase leaderboard; test access policies with at least two players and document the privacy policy. A client-reported score is not cheat-proof.
