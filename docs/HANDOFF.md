# Handoff — Tanuki Rush Mobile Edition

Updated 2026-11-18. For user-facing build and release instructions, see [README](../README.md).

## Current scope

- Original Three.js game by tanuu5, MIT. This edition supplies a Flutter Android shell and adds English UI, offline daily missions, local token rewards, cosmetic boost trails, ranks, streaks and settings. Preserve the original credits and licenses.
- Browser preview, tests and production bundle use `tanuki-rush/`; run `python3 tools/build_web_assets.py` after game edits to refresh `mobile/assets/web/`.
- No online database or leaderboard is connected. [DATABASE.md](DATABASE.md) recommends Supabase for a future opt-in online phase and outlines required security and privacy work.
- Android progress/settings are stored in private SQLite (`LocalGameDatabase.kt`) through a serial, validated Flutter bridge. `src/storage.js` bootstraps before the Game/haptics read anything, migrates the old fixed-origin keys once, and replays a revisioned localStorage pending-write journal. SQLite wins after migration; failures block startup or show a native retry warning. Browser builds still use localStorage. The renderer remains Three.js in a WebView.
- `gameStoragePort` is fixed at `43853`; do not change it: legacy keys and the journal are scoped to the full origin. Old random-port builds cannot automatically migrate saves. A port conflict fails closed. Uninstall, app-data clearing, key changes and disk failures can still lose progress; there is no supported backup.
- Android reminders are opt-in and off by default. `flutter_local_notifications` requires Java desugaring in the app Gradle file.

- `armed but never fired` is ambiguous, and that ambiguity is the current blocker rather than the hang itself. It happens both when the Android UI thread stops running after `onCreate` (the real field bug: no Dart, dead back button) and when a runner is too starved to schedule anything. 1.0.7+8 therefore adds a **heartbeat** — one `native-watchdog: heartbeat N at <ms>ms, ui=false` line every 5 s while waiting. Heartbeats that stop after `armed` mean a blocked main thread; heartbeats that keep arriving mean the engine genuinely never paints. `ci_boot_test.sh` counts them, quotes the last one, and records how long the emulator needed to reach `boot_completed`, a usable package service and a stopped boot animation, so a slow runner can no longer masquerade as a hung app.
- New leading suspect, unverified: `flutter_inappwebview` plugin registration runs during `FlutterActivity.onCreate`, before any frame, and bringing up the WebView provider on a fresh or just-updated install can trigger `dex2oat` work on the main thread for tens of seconds. That single mechanism would explain the field report (navy, dead back button, process alive), the intermittency (only after a WebView update or first install), the device spread, and the CI pattern (fresh emulator images). It is a suspect and nothing more: `tools/field_diag.ps1` greps for `dex2oat|WebViewFactory|WebViewChromium` so the next report either confirms or kills it.

- **The CI boot test measures the wrong end state.** It passes on the behaviour this phone shows, because it only waits for `[tanuki] first-frame-painted`. It cannot be made to gate on a rendered game (emulators have no Mali GPU, so the WebGL canvas may legitimately stay empty), so it reports the screen instead of gating on it — and its first attempt at that was itself wrong. It compared the PNG's byte count against a 50 KB threshold and run 44037904859 duly reported `boot-pass.png is only 15366 bytes`, which was then read as "CI has been green while reproducing the field symptom". **That reading was false and is retracted.** Run 44044845761 decoded the same kind of screenshot: `640x320 distinct=114 centre=#F1F0F7 flat=no`. Every leg in it, passing and failing alike, produced a 14-17 KB PNG at 640x320 holding 83 to 124 distinct colours with the pale grey centre of a *system* surface. Size cannot mean flatness: this repository's own 72x72 launcher icon is 597 bytes and holds 21 colours. `tools/png_summary.py` (standard library only; round-trip verified against every PNG filter type and colour types 0/2/4/6) is now the authority via `describe_screen`, and the threshold survives only as a fallback for images the decoder cannot read. **Nothing in CI has reproduced the field symptom.** The same run also asserted `UI thread STOPPED running after onCreate (blocked, not merely slow)` on an emulator whose readiness was `boot=6s package=26s bootanim=414s` — the boot animation was still running after seven minutes — so readiness above 120 s now appends an explicit `UNRELIABLE` marker, because claiming a blocked main thread on a machine that never became healthy is the same move that produced the dex2oat and API-37 dead ends. `build-field-apks` supplies the two APKs that can actually answer the question, both arm64 and both from one runner so they share the debug signing key and the phone can switch between them without uninstalling: `tanuki-rush-arm64-release-impeller-off.apk` and `tanuki-rush-arm64-debug-inspectable.apk` (debug builds set `isInspectable`, so `chrome://inspect` can read the WebView console and the canvas state on the real device).
- 1.0.6 adds a **native boot watchdog** (`BootWatchdog.kt`, wired in `MainActivity.onCreate`). `FlutterActivity` swaps `LaunchTheme` for `NormalTheme` before Flutter draws anything, so a pre-frame hang shows exactly what the user reported: the empty `#0A1A44` window background with a dead back button. Dart timeouts cannot fire because the Dart UI never runs. The watchdog polls `FlutterRenderer.isDisplayingFlutterUi()` every 500 ms and, after 12 s with no frame, adds a plain Android view (built in code, no new resources) over the content view with the device model, Android release, API level, how long it waited, and Retry/Close; it removes that view if a frame ever arrives, so it can never trap a working game. Timing logic has no Android imports and is covered by `BootWatchdogTest` in the ordinary JVM unit-test run. Verified in CI: the API 34 boot test still passes with the watchdog installed, and the Kotlin compiles. **This does not fix the engine hang** — it ends the silent dead screen and turns it into a photographable field report.
- The Impeller experiment ran for the first time in run 43544608371. `build-impeller-off` succeeded, which means `tools/patch_disable_impeller.py` injected the opt-out and `aapt2 dump xmltree` found `io.flutter.embedding.android.EnableImpeller` in the **built** manifest — Flutter 3.47.9 still honours the key at merge time. `Impeller-off boot test (API 36)` **passed**, so disabling Impeller does not stop startup on the newest testable image. `(API 34)` failed at the *install* phase, not at first frame, with the identical APK installing fine on API 36 in the same run — a cold-boot race on the package manager, which is why the script now waits for `service check package`, waits for the boot animation to stop, and retries the install three times. **The experiment is therefore inconclusive about whether Impeller-off is safe on older devices, and it has produced no evidence that Impeller is the cause.** Do not ship the opt-out on the strength of this.
- **2026-11-18: 1.0.8+9 closes one mechanism and makes the two separable on the glass.** The page could hang forever inside `Game.precompile()`: it awaited `renderer.compileAsync(...)` with no time limit, and `await` on a promise that never settles cannot be caught — the surrounding `try` handles a rejection, not a hang. A driver that wedges while compiling shaders therefore leaves `.loading` on screen permanently: a flat navy screen with a healthy process and audio threads still ticking, which is the reported symptom to the letter. `precompile()` now races the compile against an 8 s budget (`Game.PRECOMPILE_BUDGET_MS`) inside a `try/finally` that always clears the timer, and over budget the game continues and compiles shaders on demand during the first frames — a stutter, not a dead screen. `tanuki-rush/test/boot-tracer.test.js` plus the race cases pin the semantics: a never-settling compile is abandoned, a fast one is used, a rejection still propagates as a rejection rather than a false timeout, and no timer is left pending.
- Alongside the fix, the loading screen now reports itself, because the decisive fact has always been *whether the page is alive* and no screenshot at 640x320 or 2992x1344 could say. `src/core/bootTracer.js` publishes `window.__tanukiBoot()` (`stage`, `ms`, `totalMs`, `stalled`, `samples`, `note`), the loading screen prints the live stage in `#FF4FD8` — a magenta used nowhere else in the game — and switches to a blinking yellow `STALLED IN <stage> FOR n.n s` after 6 s (`STALL_AFTER_MS`). `GameScreen` polls that hook once a second and prints `[tanuki] page-boot: {…}` with `print`, not `debugPrint`, so the breadcrumbs exist in a release APK too; the poller cancels itself at `stage == ready` or after `maxBootPolls`, because `totalMs` changes every second and an unconditional poll would bury the lines that matter. Page console errors and warnings are forwarded the same way (`[tanuki-web]`, clipped to 240 characters). `fail()` now removes `.loading` first — it shared the same navy background and, with no z-index of its own, could sit *under* it — and paints `#d8231d` with the failing stage and the error message in yellow. `Renderer` reports `webglcontextlost`/`webglcontextrestored` into the same trace.
- **What the next field report will prove, from one photograph.** Magenta stage text: the page is alive, and the stage names the call it is inside. Yellow `STALLED IN <stage>`: the page is alive and hung, with the hang located — and if it reads `shaders`, the fix above is what should have prevented it, which is itself decisive. Flat navy with **no** magenta text anywhere: the page is not being drawn at all, which leaves the platform-view path (Impeller, `useHybridComposition`) as the only candidate and makes `tanuki-rush-arm64-release-impeller-off.apk` the next install. Red: the boot threw, with the stage and message on screen. `ci_boot_test.sh` reads the same breadcrumb (`page_boot_report`) and emits the last stage as a `::notice::` on both the pass and failure paths, so an emulator that hangs in `compileAsync` will now say so instead of passing silently — that is a notice, not a gate, until there is evidence it is stable enough to be one.
- Rejected: the unmerged branch `arena/edef3682-tanuki-rush` (1d21f7f, "Fix: Pixel 8 Pro / Android 17 blue status bar & splash freeze"). It placed `android:windowDrawsSystemBarBackgrounds` and `android:fitsSystemWindows` on `<activity>`, where they are not activity attributes (aapt2 links them because both exist in the framework, and the platform then ignores them); added `<meta-data android:name="android:windowLayoutInDisplayCutoutMode">`, which nothing reads — cutout mode is a theme `<item>` and belongs in `values-v27/styles.xml`; changed a real newline into a literal `\n` in the gate's error string; and moved `_configureSystemUI()` from `main()` into `_GameGateState.initState()`, which cannot matter because both run after `runApp()`. Nothing in it touches a pre-frame hang. The sound parts of the abandoned work — 92a8688 (1.0.5 release notes) and 7c07031 (the newer-API CI legs) — were cherry-picked into this branch instead.

## Which blue screen is which

Every blue surface the app can show, and what else is on it. Only two are flat, so "pure blue with nothing" is already a narrowing — and the exact colour is decisive, which is why `tools/field_diag.ps1` samples pixels instead of trusting a description of "blue".

| Surface | Colour | Also visible | Meaning |
|---|---|---|---|
| Android `NormalTheme` window background (`game_night`) and `launch_background.xml` | `#0A1A44` navy | **nothing** | pre-first-frame hang: no Dart ran, back button dead |
| `_GameGate` while the asset server starts (`main.dart`) | `#0A1A44` navy | 32 px spinner | Dart is up, waiting on `startGameServer()` |
| `_GameGate` error branch | navy | message + Retry | the loopback server could not bind port 43853 |
| `GameScreen._LoadingOverlay` | navy | 64 px leaf, progress bar, "TANUKI RUSH" | WebView created, `onLoadStop` has not fired |
| `GameScreen._ErrorOverlay` | navy | icon + message + Retry | WebView reported a main-frame error |
| Native boot watchdog (1.0.6+) | navy | "TANUKI RUSH", device details, Retry/Close | 12 s with no first frame |
| Web `.loading` (1.0.8+) | `#0a1a44` over `og-image.jpg` | "LOADING…" in 28 px white **plus a `#FF4FD8` stage line** | `Game.start()` has not finished; the stage line names where it is, and the page is provably alive |
| Web `.loading` stalled (1.0.8+) | `#0a1a44` over `og-image.jpg` | blinking `#FFE14F` "STALLED IN \<stage\> FOR n.n s" | the page is alive and hung inside `<stage>` for over 6 s |
| Web `fail()` alert (1.0.8+) | **`#d8231d` red** | message in white, stage and error in `#FFE14F` | the boot threw; `.loading` is removed first so it cannot be hidden |
| Web `.loading` (`src/ui/HUD.js`) | `#0a1a44` over `og-image.jpg` | "LOADING…" in 28 px white | `Game.start()` never finished |
| Web `fail()` alert (`src/main.js`) | `#0a1a44` | WebGL or storage message | WebGL2 missing, or storage failed to open |
| WebGL clear colour (`Renderer.setClearColor`) | **`#BFE3FF` pale blue** | **nothing** | context exists, the scene never rendered |
| the page's own background (`hud.css` `html, body`) | **`#000000` black** | **nothing** | the WebView IS visible, only its canvas is not drawing |

Three consequences worth keeping. A **pale** blue screen is a different bug from a navy one (GPU/WebGL inside the WebView rather than a Flutter pre-frame hang). A **black** screen means the WebView is being presented and only its canvas is failing, while a **navy** one with Flutter painting means the WebView is *not* being presented at all — the 2026-11-17 field report is that last case. And any navy surface *with* content means an error path is already doing its job, so the screenshot is the answer.

## Next steps

1. Read the boot verdicts on the newest run before anything else: `Boot test (API 36, run 1/2/3)` and `Impeller-off boot test (API 34)` / `(API 36)`. The API 36 pass rate says whether 1.0.6 changed something or that image is simply flaky; API 35 passed on its first and only sample so far. The Impeller-off pair says whether opting out is a *safe* fallback (it must still boot on API 34) and whether it helps where the hang shows up. If Impeller-off boots on both while the normal build fails on API 36 in the same run, ship the opt-out; if it fails on API 34 as well, the flag is not usable on Flutter 3.47.9 and the rasterizer theory dies with it — leaving the landscape-locked activity and WebView bring-up as the remaining suspects.
2. Keep using the phone as the instrument; it produces better evidence than CI can. Re-run the field diagnostic after installing each variant APK: `powershell -ExecutionPolicy Bypass -File tools\field_diag.ps1 -Apk <path to preview apk>` (add `-Adb C:\platform-tools\adb.exe` when adb is not on PATH). One run records the installed version, GPU and WebView provider, samples the screen every few seconds and prints exact pixel colours, pulls the watchdog breadcrumbs out of logcat, reads `dumpsys activity exit-info` for ANRs, and finally fetches the game from the phone's own loopback server through a forwarded port. It writes `tanuki-report.txt`, `tanuki-logcat.txt` and the screenshots, and prints a READING block that classifies the failure. Android 17 has no CI emulator image, so this report is the only evidence available for it.
3. Confirm the rest of the GitHub Actions run is green, then install its APK on physical phones. On the Pixel, repeatedly tap and hold BOOST during normal play, listening for both music and JUMP/BOOST, and report whether sound drops out. If it stops, try automatic recovery and Pause → Settings → Restore Audio → Reset. Crash/fall, test the one free revive and the no-revive second failure, retry from the start, and complete a run. Also check both orientations, touch controls, haptics and optional notifications.
4. On a disposable test installation, install the previous fixed-origin build, create progress/settings, then perform an **in-place update signed with the same key**. Confirm migration, restart/force-stop persistence, offline play and the native storage status. Test disk-full/error recovery where practical. Existing debug previews may have different signatures; do not uninstall a user's valuable save.
5. Obtain and securely back up a long-lived release keystore and design/test an export or backup before production. Never commit or paste credentials.
6. Only after local storage is verified, consider the opt-in Supabase leaderboard; test access policies with at least two players and document the privacy policy. A client-reported score is not cheat-proof.
